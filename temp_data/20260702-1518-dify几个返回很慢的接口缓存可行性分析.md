# Dify 离线部署接口缓存分析

## 背景

从日志看，首次访问时多个 console 接口耗时 6–8 秒，随后回落到 1 秒左右。离线环境下，最可能的慢原因是：

- 插件 Daemon（plugin daemon）首次响应慢 / 冷启动。
- 部分接口会尝试访问 Marketplace（`MARKETPLACE_ENABLED`），离线时产生网络超时。
- 模型/工具/触发器 provider 的元数据需要从插件进程或数据库实时组装。

下面按“变动频率”和“离线场景相关性”把日志里的接口分成 3 类，并给出缓存建议。

### 关于 `plugin/list/latest-versions`

这个接口在离线部署下**不应该被前端频繁调用**。它的逻辑是：

1. 先从 Redis 查每个 plugin_id 的最新版本缓存（TTL 5 分钟）。
2. 缓存不存在且 `MARKETPLACE_ENABLED=True` 时，访问 Marketplace 网络。
3. 如果 `MARKETPLACE_ENABLED=False`，直接返回 `None`。

**建议**：离线部署直接把 `MARKETPLACE_ENABLED` 设为 `false`，比代理缓存更根本。如果必须缓存该接口，可设置很短 TTL（30 秒）或直接返回固定空结果。

## 缓存实现位置建议

从日志看你的架构里有 `DifyProxyServiceImpl.java`，因此最自然的位置是在 Java 代理层加一层响应缓存：

- **只缓存 GET/HEAD 请求**。
- **按 URL + 用户 token / tenant 分区**，避免不同租户/用户串数据。
- **对 Tier 1 设置较长 TTL**，对 Tier 2 设置较短 TTL。
- **提供手动刷新入口**：在升级插件、修改模型凭证、修改系统配置后，可以调用刷新或等待 TTL 过期。

如果以后想做到更细粒度的自动失效，可以在 Dify API 层通过装饰器/Redis 缓存实现，但这需要修改 Dify 代码，当前阶段按你的要求暂不展开。

## 推荐优先缓存的 TOP 5 接口

按“收益/风险比”排序：

1. `GET /console/api/system-features` — 收益最大，完全静态。
2. `GET /console/api/spec/schema-definitions` — 完全静态，前端初始化必调。
3. `GET /console/api/workspaces/current/models/model-types/*` — 慢且调用频繁，短缓存收益高。
4. `GET /console/api/workspaces/current/tools/builtin` — 离线插件不变，短缓存收益高。
5. `GET /console/api/workspaces/current/triggers` — 同上。

---

## 风险与注意事项

1. **凭证可见性**：部分工具接口（如 `credential/info`、`credentials`）会根据当前用户过滤 `only_me` 凭证。缓存 key 必须包含用户标识。
2. **许可/企业特性**：`system-features` 里的企业版开关、branding 等会随环境变量变化，但通常只在重启后生效，TTL 可覆盖。
3. **插件安装/卸载**：Tier 2 接口在离线环境虽然变动少，但仍可能通过上传 `.difypkg` 安装新插件。需要预留手动清缓存能力。
4. **默认模型切换**：`default-model` 缓存时间不宜过长，否则用户切换默认模型后前端仍显示旧值。
5. ** Marketplace 超时**：`plugin/list/latest-versions` 的 root cause 更可能是离线访问 Marketplace，优先关闭 `MARKETPLACE_ENABLED`。
