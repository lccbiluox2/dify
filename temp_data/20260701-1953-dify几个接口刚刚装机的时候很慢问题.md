# Dify 新装机环境首次打开页面很慢问题：源码级深度分析

> 环境信息：Dify 1.14.2，社区版（SELF_HOSTED），Docker/K8s 部署
> 问题现象：新装机的环境，第一次打开 Dify 控制台页面时非常慢（超过 6 秒），但后续访问就很快
> 分析日期：2026-07-01

---

## 一、问题背景

在一个新装机的 Dify 环境中，第一次打开控制台页面（如 `/apps` 页面）时，页面加载超过 6 秒。但刷新页面或再次访问后，速度恢复正常。

通过浏览器开发者工具抓包发现，首次打开页面时会并行请求以下三个核心 API：

| API 接口 | 方法 | 说明 | 是否需要认证 |
|---------|------|------|-------------|
| `/console/api/system-features` | GET | 获取系统特性配置 | 否 |
| `/console/api/account/profile` | GET | 获取当前用户信息 | 是 |
| `/console/api/workspaces/current` | POST | 获取当前工作空间信息 | 是 |

这三个接口在首次访问时都很慢，但后续访问就快了。本文将从**后端（Python/Flask）**和**前端（Next.js/React）**两个维度，结合源码进行深度分析。

## 二、整体架构与请求链路

### 2.2 关键发现：前端 SSR 会阻塞首屏渲染

Dify 前端使用 Next.js App Router，控制台页面通过 **服务端渲染（SSR）** 预取数据。关键文件在 `web/app/(commonLayout)/hydration-boundary.tsx`：

```typescript
// web/app/(commonLayout)/hydration-boundary.tsx
export async function CommonLayoutHydrationBoundary({ children }) {
  const queryClient = getQueryClientServer()

  try {
    const context = await getServerConsoleClientContext()

    // 三个 API 并行预取，全部完成后才返回 HTML
    await Promise.all([
      queryClient.fetchQuery(serverUserProfileQueryOptions()),        // /account/profile
      queryClient.prefetchQuery(serverSystemFeaturesQueryOptions()),   // /system-features
      queryClient.prefetchQuery(serverConsoleQuery.workspaces.current.post.queryOptions({
        context,
        retry: false,
      })),                                                            // /workspaces/current
    ])
  } catch (error) {
    await handleProfileError(error)
  }

  return (
    <HydrationBoundary state={dehydrate(queryClient)}>
      {children}
    </HydrationBoundary>
  )
}
```

**这意味着浏览器在收到任何 HTML 之前，Next.js 服务端必须等待这三个 API 全部返回。** 如果后端冷启动慢，整个页面就会白屏等待。

### 2.3 AppContextProvider 使用 Suspense 阻塞渲染

在 `web/context/app-context-provider.tsx` 中，两个核心查询使用了 `useSuspenseQuery`：

```typescript
// web/context/app-context-provider.tsx
export const AppContextProvider = ({ children }) => {
  const { data: systemFeatures } = useSuspenseQuery(systemFeaturesQueryOptions())
  const { data: userProfileResp } = useSuspenseQuery(userProfileQueryOptions())
  const { data: currentWorkspaceResp } = useQuery(consoleQuery.workspaces.current.post.queryOptions())
  const langGeniusVersionQuery = useLangGeniusVersion(
    userProfileResp?.meta.currentVersion,
    !systemFeatures.branding.enabled,
  )
  // ...
}
```

`useSuspenseQuery` 会挂起组件渲染，直到数据就绪。虽然 SSR 预取已经将数据注入了 React Query 缓存，但如果预取阶段超时或失败，客户端仍需重新请求。

## 三、后端源码深度分析

### 3.1 Gunicorn 配置：单 Worker + Gevent

Docker 环境的入口脚本 `api/docker/entrypoint.sh`：

```bash
# api/docker/entrypoint.sh
exec gunicorn \
  --bind "${DIFY_BIND_ADDRESS:-0.0.0.0}:${DIFY_PORT:-5001}" \
  --workers ${SERVER_WORKER_AMOUNT:-1} \
  --worker-class ${SERVER_WORKER_CLASS:-geventwebsocket.gunicorn.workers.GeventWebSocketWorker} \
  --worker-connections ${SERVER_WORKER_CONNECTIONS:-10} \
  --timeout ${GUNICORN_TIMEOUT:-200} \
  app:socketio_app
```

默认配置（`.env.example`）：

```bash
SERVER_WORKER_AMOUNT=1        # 只有 1 个 worker 进程
SERVER_WORKER_CONNECTIONS=10  # 每个 worker 10 个并发连接
GUNICORN_TIMEOUT=360
```

**关键问题：** 默认只有 1 个 gunicorn worker，所有请求都通过这个单进程处理。虽然 gevent 提供了协程并发，但首次请求时的资源初始化（DB 连接、Redis 连接、模块导入）是串行的。

#### 3.2.2 引擎创建 vs 连接创建

在 `api/extensions/ext_database.py` 中，引擎在启动时被创建，但**连接是懒加载的**：

```python
# api/extensions/ext_database.py
def init_app(app: DifyApp):
    db.init_app(app)
    _setup_gevent_compatibility()

    # Eagerly build the engine so pool_size/max_overflow/etc. come from config
    try:
        with app.app_context():
            _ = db.engine  # 仅触发引擎创建，不会创建实际数据库连接！
    except Exception:
        logger.exception("Failed to initialize SQLAlchemy engine during app startup")
```

**`db.engine` 只创建了引擎对象（Engine），但连接池中的实际 TCP 连接是在第一次查询时才建立的。** 这就是冷启动的核心原因。

### 3.3 用户加载流程：每次认证请求的 DB 查询

在 `api/extensions/ext_login.py` 中，Flask-Login 的请求加载器：

```python
# api/extensions/ext_login.py
@login_manager.request_loader
def load_user_from_request(request_from_flask_login: Request) -> LoginUser | None:
    del request_from_flask_login

    auth_token = extract_access_token(request)

    if request.blueprint in {"console", "inner_api"}:
        if not auth_token:
            raise Unauthorized("Invalid Authorization token.")
        # JWT 解码（CPU 操作，较快）
        decoded = PassportService().verify(auth_token)
        user_id = decoded.get("user_id")
        # ...
        # 从数据库加载用户（涉及多次 DB 查询）
        logged_in_account = AccountService.load_logged_in_account(account_id=user_id)
        return logged_in_account
```

JWT 验证本身很快（`api/libs/passport.py`）：

```python
# api/libs/passport.py
class PassportService:
    def __init__(self):
        self.sk = dify_config.SECRET_KEY

    def verify(self, token):
        try:
            return jwt.decode(token, self.sk, algorithms=["HS256"])
        except jwt.ExpiredSignatureError:
            raise Unauthorized("Token has expired.")
        # ...
```

但 `load_logged_in_account` 调用了 `load_user` 方法，涉及多次数据库查询：

```python
# api/services/account_service.py
@staticmethod
def load_user(user_id: str) -> None | Account:
    # DB 查询 #1：根据 ID 查询 Account
    account = db.session.get(Account, user_id)
    if not account:
        return None

    if account.status == AccountStatus.BANNED:
        raise Unauthorized("Account is banned.")

    # DB 查询 #2：查询当前选中的 TenantAccountJoin
    current_tenant = db.session.scalar(
        select(TenantAccountJoin)
        .where(TenantAccountJoin.account_id == account.id, TenantAccountJoin.current == True)
        .limit(1)
    )
    if current_tenant:
        account.set_tenant_id(current_tenant.tenant_id)
    else:
        # DB 查询 #3（如果没有 current tenant）：查询可用的 TenantAccountJoin
        available_ta = db.session.scalar(
            select(TenantAccountJoin)
            .where(TenantAccountJoin.account_id == account.id)
            .order_by(TenantAccountJoin.id.asc())
            .limit(1)
        )
        if not available_ta:
            return None
        account.set_tenant_id(available_ta.tenant_id)
        available_ta.current = True
        db.session.commit()  # DB 写入

    # Redis 操作 + 可能的 DB 写入
    AccountService._refresh_account_last_active(account)

    # DB 查询 #4：刷新 account 对象
    db.session.refresh(account)
    db.session.close()
    return account
```

### 3.4 Redis 连接冷启动

`_refresh_account_last_active` 方法在每次认证请求时都会检查 Redis：

```python
# api/services/account_service.py
@staticmethod
@redis_fallback(default_return=True)
def _should_refresh_account_last_active(account_id: str) -> bool:
    return bool(
        redis_client.set(
            AccountService._get_account_last_active_refresh_key(account_id),
            1,
            ex=int(ACCOUNT_LAST_ACTIVE_REFRESH_INTERVAL.total_seconds()),  # 10 分钟
            nx=True,  # 只在 key 不存在时设置
        )
    )

@staticmethod
def _refresh_account_last_active(account: Account) -> None:
    now = naive_utc_now()
    refresh_before = now - ACCOUNT_LAST_ACTIVE_REFRESH_INTERVAL

    if account.last_active_at >= refresh_before:
        return

    if not AccountService._should_refresh_account_last_active(account.id):
        return  # Redis 说最近 10 分钟内已更新过，跳过

    # 如果 Redis 说需要更新，执行 DB 写入
    db.session.execute(
        update(Account)
        .where(Account.id == account.id, Account.last_active_at < refresh_before)
        .values(last_active_at=now, updated_at=func.current_timestamp())
    )
    db.session.commit()
```

首次请求时，Redis 客户端也需要建立 TCP 连接。虽然 Redis 操作本身很快（亚毫秒级），但连接建立的过程（TCP 握手 + 认证）在冷启动时会增加几十毫秒到几百毫秒的延迟。

### 3.5 Python 模块懒加载

Dify 代码库中大量使用了**延迟导入**（lazy import），即在实际使用时才导入模块。这些导入在首次请求时会被触发：

```python
# api/controllers/console/wraps.py - 在函数内部导入
def is_allow_transfer_owner(view):
    @wraps(view)
    def decorated(*args, **kwargs):
        from libs.workspace_permission import check_workspace_owner_transfer_permission
        # ...

# api/services/account_service.py - 在函数内部导入
def _try_join_enterprise_default_workspace(account_id: str) -> None:
    from services.enterprise.enterprise_service import try_join_default_workspace
    try_join_default_workspace(account_id)
```

Python 的模块导入机制在首次导入时需要：
1. 在文件系统中查找 `.py` 文件
2. 编译为字节码（如果没有 `.pyc` 缓存）
3. 执行模块级代码
4. 注册到 `sys.modules`

后续请求直接从 `sys.modules` 缓存中获取，几乎零开销。

### 3.6 外部版本检查 HTTP 调用（潜在的 3 秒延迟）

`/version` 接口会调用外部 URL 检查更新：

```python
# api/controllers/console/version.py
@console_router.get("/version", response_model=VersionResponse, tags=["console"])
def check_version_update(query: VersionQuery) -> VersionResponse:
    check_update_url = dify_config.CHECK_UPDATE_URL

    result = VersionResponse(
        version=dify_config.project.version,
        release_date="",
        release_notes="",
        can_auto_update=False,
        features=VersionFeatures(
            can_replace_logo=dify_config.CAN_REPLACE_LOGO,
            model_load_balancing_enabled=dify_config.MODEL_LB_ENABLED,
        ),
    )

    if not check_update_url:
        return result  # 如果没有配置 CHECK_UPDATE_URL，直接返回

    try:
        # 外部 HTTP 调用，超时 10 秒，连接超时 3 秒
        response = httpx.get(
            check_update_url,
            params={"current_version": query.current_version},
            timeout=httpx.Timeout(timeout=10.0, connect=3.0),
        )
        content = response.json()
    except Exception as error:
        logger.warning("Check update version error: %s.", str(error))
        result.version = query.current_version
        return result
    # ...
```

**在内网/离线环境中，如果 `CHECK_UPDATE_URL` 配置了一个不可达的地址，这个接口会阻塞最多 3 秒（连接超时）。**

前端通过 `useLangGeniusVersion` 调用这个接口：

```typescript

export const useLangGeniusVersion = (currentVersion?: string | null, enabled?: boolean) => {
  return useQuery<LangGeniusVersionResponse>({
    queryKey: commonQueryKeys.langGeniusVersion(currentVersion || undefined),
    queryFn: () => get<LangGeniusVersionResponse>('/version', {
      params: { current_version: currentVersion }
    }),
    enabled: !!currentVersion && (enabled ?? true),
  })
}
```

### 3.7 before_request 钩子

在 `api/app_factory.py` 中，Flask 应用注册了 `before_request` 钩子：

```python
# api/app_factory.py
@dify_app.before_request
def before_request():
    init_request_context()
    RecyclableContextVar.increment_thread_recycles()

    # 企业版的 License 检查（社区版跳过）
    if dify_config.ENTERPRISE_ENABLED:
        is_console_api = request.path.startswith("/console/api/")
        is_webapp_api = request.path.startswith("/api/")

        if is_console_api or is_webapp_api:
            if is_console_api:
                is_exempt = any(request.path.startswith(p) for p in _CONSOLE_EXEMPT_PREFIXES)
            else:
                is_exempt = request.path.startswith("/api/system-features")

            if not is_exempt:
                try:
                    # 检查 License 状态（有 Redis 缓存）
                    license_status = EnterpriseService.get_cached_license_status()
                    if license_status in (LicenseStatus.INACTIVE, LicenseStatus.EXPIRED, LicenseStatus.LOST):
                        raise UnauthorizedAndForceLogout(...)
                except UnauthorizedAndForceLogout:
                    raise
                except Exception:
                    logger.exception("Failed to check enterprise license status")
                    raise UnauthorizedAndForceLogout(...)
```

对于**社区版（SELF_HOSTED）**，这个钩子基本上是空操作（只做日志上下文初始化），不会造成明显延迟。

对于**企业版**，`EnterpriseService.get_cached_license_status()` 有 Redis 缓存：

```python
# api/services/enterprise/enterprise_service.py
@classmethod
def get_cached_license_status(cls) -> LicenseStatus | None:
    """Get enterprise license status with Redis caching to reduce HTTP calls.

    Caches valid statuses (active/expiring) for 10 minutes and invalid statuses
    (inactive/expired/lost) for 30 seconds.
    """
    if not dify_config.ENTERPRISE_ENABLED:
        return None

    cached = cls._read_cached_license_status()  # 先读 Redis 缓存
    if cached is not None:
        return cached

    return cls._fetch_and_cache_license_status()  # 缓存未命中时调用企业 API
```

首次请求时缓存为空，需要调用企业 API（HTTP 请求），这可能需要几秒。

### 3.8 Nginx 代理配置

Nginx 配置中关闭了 `proxy_buffering`，这意味着 Nginx 不会缓冲后端响应，而是直接流式转发：

```nginx
# docker/nginx/proxy.conf.template
proxy_set_header Host $host;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Forwarded-Port $server_port;
proxy_http_version 1.1;
proxy_set_header Connection "";
proxy_buffering off;          # 关闭缓冲，流式转发
proxy_read_timeout ${NGINX_PROXY_READ_TIMEOUT};
proxy_send_timeout ${NGINX_PROXY_SEND_TIMEOUT};
```

这个配置本身不影响首次加载速度，但 `Connection ""` 配合 `proxy_http_version 1.1` 启用了 keep-alive，后续请求可以复用连接。

## 四、前端源码深度分析

### 4.1 React Query 缓存策略：5 分钟 staleTime

React Query 客户端配置了 5 分钟的 `staleTime`：

```typescript
// web/context/query-client-server.ts
import { QueryClient } from '@tanstack/react-query'
import { cache } from 'react'

const STALE_TIME = 1000 * 60 * 5 // 5 分钟

export function makeQueryClient() {
  return new QueryClient({
    defaultOptions: {
      queries: {
        staleTime: STALE_TIME,
      },
    },
  })
}

export const getQueryClientServer = cache(makeQueryClient)
```

**这意味着：**
- **首次加载**：React Query 缓存为空，必须发起 API 请求
- **5 分钟内再次加载**：数据被认为是新鲜的，直接从内存缓存返回，不发 API 请求
- **5 分钟后**：数据变为过期（stale），但仍然立即从缓存返回，同时在后台异步刷新

这是后续访问变快的**最直接原因**。

### 4.2 system-features 查询配置

### 4.3 account/profile 查询配置（服务端）


### 4.4 服务端到 API 的请求转发

Next.js 服务端通过 `service/server.ts` 将浏览器的 Cookie 和 CSRF Token 转发给 Flask API：

```typescript
// web/service/server.ts
export const getServerConsoleClientContext = async (): Promise<ServerConsoleClientContext> => {
  const { cookies, headers } = await import('@/next/headers')
  const requestHeaders = await headers()
  const cookieStore = await cookies()

  return {
    cookie: requestHeaders.get('cookie') || undefined,
    csrfToken: cookieStore.get(CSRF_COOKIE_NAME())?.value,
  }
}

const serverConsoleLink = new OpenAPILink<ServerConsoleClientContext>(consoleRouterContract, {
  url: getServerConsoleApiPrefix,
  headers: ({ context }) => createServerConsoleRequestHeaders(context),
  fetch: (request, init) => {
    if (request.body && !request.headers.has('content-type'))
      request.headers.set('Content-Type', 'application/json')

    return globalThis.fetch(request, {
      ...init,
      cache: 'no-store',  // 不使用 HTTP 缓存
    })
  },
  // ...
})
```

**首次请求时**，Next.js 服务端到 Flask API 的 HTTP 连接也需要建立（TCP 握手），后续请求通过 keep-alive 复用连接。

### 4.5 前端请求的 fetch 配置

前端所有 API 请求都设置了 `cache: 'no-store'`，这意味着浏览器不使用 HTTP 缓存：

```typescript
// web/service/base.ts (通过 consoleLink 的 fetch 配置)
fetch: (input, init) => {
  return request(input.url, init, {
    fetchCompat: true,
    request: input,
  })
}
```

但由于 React Query 的内存缓存（5 分钟 staleTime），在缓存有效期内不会发起 HTTP 请求，所以 `no-store` 不影响后续加载速度。

## 五、冷启动 vs 热缓存：完整流程对比

### 5.1 首次加载流程（慢，6 秒+）

```
1. 浏览器请求页面 → Nginx → Next.js 服务端
   │
2. Next.js SSR: CommonLayoutHydrationBoundary 执行
   │
   ├─ 并行发起 3 个 API 请求（Next.js → Flask API）
   │   │
   │   ├─ /account/profile (认证接口)
   │   │   │
   │   │   ├─ before_request 钩子
   │   │   │   └─ init_request_context() (轻量)
   │   │   │
   │   │   ├─ setup_required 装饰器
   │   │   │   └─ DB 查询: SELECT * FROM dify_setup LIMIT 1
   │   │   │      └─ 【冷启动】创建数据库连接 (TCP + 认证 + 会话) ~100-500ms
   │   │   │
   │   │   ├─ login_required (Flask-Login request_loader)
   │   │   │   ├─ PassportService().verify(token)  # JWT 解码 ~1ms
   │   │   │   └─ AccountService.load_user(user_id)
   │   │   │       ├─ DB 查询: SELECT * FROM account WHERE id = ?  ~5-20ms
   │   │   │       ├─ DB 查询: SELECT * FROM tenant_account_join WHERE ... ~5-20ms
   │   │   │       ├─ Redis: SET NX (检查 last_active) ~2-50ms
   │   │   │       │   └─ 【冷启动】创建 Redis 连接 ~10-100ms
   │   │   │       ├─ DB 查询: REFRESH account ~5-20ms
   │   │   │       └─ db.session.close()
   │   │   │
   │   │   ├─ account_initialization_required
   │   │   │   └─ 检查 current_user.status (已加载，无额外查询)
   │   │   │
   │   │   ├─ enterprise_license_required
   │   │   │   └─ FeatureService.get_system_features() (社区版: 仅读配置，快)
   │   │   │
   │   │   └─ 返回用户 profile JSON
   │   │
   │   ├─ /system-features (无需认证)
   │   │   ├─ 无 setup_required (不需要认证)
   │   │   ├─ FeatureService.get_system_features()
   │   │   │   └─ 仅读 dify_config 配置 (内存操作，快)
   │   │   └─ 返回系统特性 JSON
   │   │
   │   └─ /workspaces/current (认证接口)
   │       ├─ setup_required (同上，DB 查询 - 复用已建立的连接)
   │       ├─ login_required (同上，DB 查询 - 复用已建立的连接)
   │       ├─ account_initialization_required
   │       └─ WorkspaceService.get_tenant_info(tenant)
   │           └─ 返回工作空间信息
   │
3. Next.js 收到所有 API 响应 → dehydrate → 生成 HTML
   │
4. 浏览器收到 HTML → 下载 JS/CSS bundles (~1-3s 首次)
   │
5. React Hydration → 页面可交互
   │
6. useLangGeniusVersion 触发 /version 请求 (客户端)
   └─ 可能的外部 HTTP 调用 (最多 3s 超时)
```

### 5.2 后续加载流程（快，<1 秒）

```
1. 浏览器请求页面 → Nginx → Next.js 服务端
   │
2. Next.js SSR: CommonLayoutHydrationBoundary 执行
   │
   ├─ 并行发起 3 个 API 请求
   │   │
   │   ├─ /account/profile
   │   │   ├─ setup_required → DB 查询 (连接池已有连接，~1-5ms)
   │   │   ├─ login_required → JWT 解码 + DB 查询 (~5-20ms)
   │   │   └─ 返回 JSON
   │   │
   │   ├─ /system-features → 读配置 (~1ms)
   │   └─ /workspaces/current → DB 查询 (~5-20ms)
   │
   │   全部完成：~50-200ms
   │
3. Next.js 生成 HTML → 浏览器
   │
4. 浏览器 → React Hydration
   │
5. React Query 缓存命中 (5 分钟内)
   └─ 直接从内存返回数据，不发 API 请求
   │
6. JS bundles → 浏览器缓存命中 (~0ms)
   │
7. HTTP 连接 → keep-alive 复用 (~0ms)
   │
8. /version 请求 → React Query 缓存命中 (5 分钟内，不发请求)
```

### 5.3 五分钟后再次加载（仍然快）

```
1-4. 同后续加载流程 (SSR 仍然发 API 请求，但后端连接池已热)
   │
5. React Query: 数据已过期 (stale)
   ├─ 立即从缓存返回数据 → 页面秒开
   └─ 后台异步刷新数据 → 用户无感知
```

## 六、根因总结

| 序号 | 原因 | 影响程度 | 首次耗时 | 后续耗时 |
|------|------|---------|---------|---------|
| 1 | **数据库连接池冷启动** | ★★★★★ | 100-500ms | ~1-5ms |
| 2 | **Redis 连接冷启动** | ★★★☆☆ | 10-100ms | ~1-2ms |
| 3 | **Python 模块懒加载** | ★★★☆☆ | 50-200ms | ~0ms |
| 4 | **外部版本检查 HTTP 调用** | ★★★★☆ | 0-3000ms | 0ms (缓存) |
| 5 | **Next.js SSR 阻塞渲染** | ★★★★☆ | 取决于后端 | 取决于后端 |
| 6 | **JS Bundle 首次下载** | ★★★☆☆ | 1000-3000ms | ~0ms (浏览器缓存) |
| 7 | **HTTP 连接建立** | ★★☆☆☆ | 10-50ms | ~0ms (keep-alive) |
| 8 | **React Query 5 分钟缓存** | ★★★★★ | 无缓存，发请求 | 有缓存，不发请求 |

**核心结论：** 首次加载慢的本质是**冷启动问题**——后端的数据库/Redis 连接池为空、Python 模块未加载，前端的 React Query 缓存为空、JS Bundle 未下载。后续加载快是因为所有这些资源都已被缓存或预热。

## 七、优化建议

### 7.1 后端优化

#### 7.1.1 禁用或缩短版本检查超时

在 `.env` 中设置：

```bash
# 完全禁用版本检查（推荐内网/离线环境使用）
CHECK_UPDATE_URL=
```

或者修改源码缩短超时时间（`api/controllers/console/version.py`）：

```python
# 将 connect 超时从 3 秒缩短到 1 秒
timeout=httpx.Timeout(timeout=5.0, connect=1.0)
```

#### 7.1.2 增加 Gunicorn Worker 数量

```bash
# .env
SERVER_WORKER_AMOUNT=2  # 或更多（根据 CPU 核心数）
```

#### 7.1.3 预热后端连接池

在 API 容器启动后，通过 health check 或 init 脚本预热连接：

```bash
# 在 docker-entrypoint.sh 或 K8s postStart hook 中添加
curl -s http://localhost:5001/console/api/system-features > /dev/null
curl -s http://localhost:5001/health > /dev/null
```

#### 7.1.4 数据库连接池优化

```bash
# .env
SQLALCHEMY_POOL_PRE_PING=true   # 开启连接健康检查
SQLALCHEMY_POOL_SIZE=10         # 根据实际负载调整
SQLALCHEMY_MAX_OVERFLOW=5
```

### 7.2 前端优化

#### 7.2.1 调整 React Query staleTime

如果希望更长时间的缓存命中，可以增加 staleTime：

```typescript
// web/context/query-client-server.ts
const STALE_TIME = 1000 * 60 * 30 // 30 分钟（从 5 分钟增加）
```

#### 7.2.2 非关键数据改为客户端加载

`/version` 接口的版本检查可以改为异步加载，不阻塞首屏渲染：

```typescript
// web/context/app-context-provider.tsx
// 将 useLangGeniusVersion 改为非阻塞的 useQuery（而非 useSuspenseQuery）
const langGeniusVersionQuery = useQuery({
  ...useLangGeniusVersionOptions(userProfileResp?.meta.currentVersion),
  enabled: !!userProfileResp?.meta.currentVersion,
})
```

### 7.3 部署优化

#### 7.3.1 配置 Nginx 静态资源缓存

```nginx
# 为 JS/CSS 添加长期缓存
location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff|woff2|ttf|eot)$ {
    proxy_pass http://web:3000;
    proxy_cache_valid 200 1y;
    add_header Cache-Control "public, max-age=31536000, immutable";
}
```

#### 7.3.2 启用 HTTP/2

如果使用 HTTPS，在 Nginx 中启用 HTTP/2 可以并行下载资源：

```nginx
server {
    listen 443 ssl http2;
    # ...
}
```

## 八、验证方法

### 8.1 后端冷启动验证

在 API 容器启动后，立即执行以下命令测量各接口响应时间：

```bash
# 第一次请求（冷启动）
time curl -s http://localhost:5001/console/api/system-features > /dev/null
time curl -s -H "Authorization: Bearer <token>" http://localhost:5001/console/api/account/profile > /dev/null
time curl -s -X POST -H "Authorization: Bearer <token>" http://localhost:5001/console/api/workspaces/current > /dev/null

# 第二次请求（热缓存）
time curl -s http://localhost:5001/console/api/system-features > /dev/null
time curl -s -H "Authorization: Bearer <token>" http://localhost:5001/console/api/account/profile > /dev/null
```

如果第一次明显比第二次慢，说明是后端冷启动问题。

### 8.2 版本检查验证

```bash
# 检查 CHECK_UPDATE_URL 是否配置
docker exec -it <api_container> env | grep CHECK_UPDATE_URL

# 直接测试版本检查接口的响应时间
time curl -s "http://localhost:5001/console/api/version?current_version=1.14.2"
```

### 8.3 前端缓存验证

在浏览器 DevTools 的 Network 面板中：
1. 首次加载页面，观察 3 个 API 请求的响应时间
2. 刷新页面，观察是否发起了新的 API 请求（React Query 缓存命中时不发请求）
3. 等待 5 分钟后刷新，观察是否先显示旧数据再更新（stale-while-revalidate）
