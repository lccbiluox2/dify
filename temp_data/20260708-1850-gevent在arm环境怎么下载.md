# aarch64 环境下载 gevent Wheel 包实录：一次成功的背后是 x86 踩过的坑

## 背景：从 Dify 插件部署到跨架构离线包准备

在部署 Dify 插件及相关 Python 服务时，`gevent` 作为核心并发库几乎是必装依赖。我们的生产环境同时包含 x86_64 和 aarch64 两种架构的节点，且均处于内网受限网络中，无法直接执行 `pip install`，必须提前在构建机上下载好完整的 Wheel 包（含所有依赖），再离线分发安装。

在前一篇文章《x86 环境下载 gevent Wheel 包排错实录》中，我们经历了三轮排查才在 x86_64 环境下成功获取 wheel：

1.  **PEP 668 报错**：`uv run` 临时环境中手动升级 pip 被拒绝
2.  **No matching distribution found**：原生架构下误用 `--platform` 参数导致标签匹配失败
3.  **最终修复**：改用 `pip wheel` 去掉跨平台参数，让 pip 自主匹配

有了 x86 的经验教训，我们在处理 aarch64 环境时避开了所有已知陷阱。本文将完整记录 aarch64 环境下**一次成功**下载 `gevent==25.5.1` 的全过程，并解释为什么这次能如此顺利。

---

## 为什么 aarch64 能一次成功

在进入实操之前，先总结 x86 排查沉淀的三条原则，这正是本次零报错的基础：

| 原则 | x86 踩坑原因 | aarch64 正确做法 |
| :--- | :--- | :--- |
| 原生架构不加 `--platform` | 加了导致标签匹配失败 | 当前机器就是 aarch64，直接用 `pip wheel` |
| 用 `--with` 注入 pip 版本 | 临时环境中 `pip install --upgrade` 触发 PEP 668 | `--with 'pip>=25.0'` 创建环境时直接带入 |
| 用 `pip wheel` 替代 `pip download` | `download` 对参数组合更敏感 | `wheel` 自动解析依赖、优先预编译、可回退源码 |

> 💡 **核心认知**：只要你在目标架构的原生机器上操作，无论 x86_64 还是 aarch64，命令完全一致。`--platform` 参数只在"当前机器架构 ≠ 目标架构"的交叉下载场景中才需要。

## 操作流程

### 步骤一：创建输出目录

```bash
mkdir -p ./tmp/wheels-aarch64/
```

### 步骤二：执行下载命令

```bash
uv run --python 3.12 --with 'pip>=25.0' -- \
  pip wheel gevent==25.5.1 \
    --wheel-dir ./tmp/wheels-aarch64/
```

## 输出日志中的关键信息解读

### PyPI 上确实有 aarch64 预编译 wheel

```text
Downloading gevent-25.5.1-cp312-cp312-manylinux_2_17_aarch64.manylinux2014_aarch64.whl
```

这行日志证实 `gevent==25.5.1` 在 PyPI 上提供了 aarch64 的预编译包。这意味着我们**不需要从源码编译**，也无需安装 `gcc`、`python3-devel`、`libffi-devel` 等编译工具链。这对于精简容器镜像和生产环境安全加固非常重要。

### 网络超时与断点续传

```text
WARNING: Connection timed out while downloading.
WARNING: Attempting to resume incomplete download (1.0 MB/1.8 MB, attempt 1)
...
WARNING: Attempting to resume incomplete download (1.6 MB/1.8 MB, attempt 2)
```

下载过程中出现了两次连接超时，pip 自动进行了断点续传重试并最终成功。这说明：

-   pip 内置的重试机制对网络波动有足够的容错能力
-   如果网络环境持续不稳定，可以考虑配置国内镜像源加速

### 依赖自动解析

`pip wheel` 自动拉取了 `greenlet`、`zope.event`、`zope.interface` 三个依赖，且全部命中了 aarch64 对应的预编译 wheel 或纯 Python 包，无需手动指定。

| 维度 | x86_64 | aarch64 |
| :--- | :--- | :--- |
| 尝试次数 | 3 次（2 次报错） | 1 次成功 |
| 最终命令 | 完全相同 | 完全相同 |
| 预编译 wheel 可用性 | ✅ 有 | ✅ 有 |
| gevent whl 大小 | 2.0 MB | 1.8 MB |
| greenlet whl 大小 | 614 KB | 604 KB |
| 是否需要编译工具链 | 否 | 否 |
| 网络状况 | 稳定 | 有超时，pip 自动续传成功 |

> ⚠️ **重要提醒**：aarch64 的预编译 wheel 覆盖率整体低于 x86_64。本次 `gevent` 恰好提供了 aarch64 包，但如果遇到没有预编译包的依赖，`pip wheel` 会自动回退到源码编译，届时需要提前安装编译工具链：
> ```bash
> # CentOS/RHEL/AlmaLinux
> yum install -y gcc python3-devel libffi-devel
> # Debian/Ubuntu
> apt install -y build-essential python3-dev libffi-dev
> ```

## 经验沉淀

1.  **经验可以跨架构复用**：x86 排查中总结的"原生架构不加 `--platform`"、"用 `--with` 注入 pip"、"用 `pip wheel` 替代 `pip download`"三条原则，在 aarch64 上完全适用，且直接带来了一次成功的结果。
2.  **不要假设 aarch64 一定缺包**：虽然 aarch64 生态不如 x86 完善，但主流库（如 gevent、greenlet）近年来已普遍提供 aarch64 预编译 wheel。遇到问题时应先验证包是否存在，而非默认需要源码编译。
3.  **网络超时无需恐慌**：pip 的断点续传机制足够可靠，短暂的 `Connection timed out` 警告不代表失败，等待自动重试即可。如果频繁超时，再考虑换源或增加 `--timeout` 参数。
4.  **验证文件名中的架构标识**：下载完成后务必检查 `.whl` 文件名是否包含正确的架构标签（如 `aarch64`），避免将 x86 包误用于 ARM 环境导致运行时崩溃。

### 离线安装验证命令

将 `./tmp/wheels-aarch64/` 拷贝至目标 aarch64 机器后，执行：

```bash
pip install --no-index --find-links=./tmp/wheels-aarch64/ gevent==25.5.1
```

至此，aarch64 环境下 `gevent==25.5.1` 的 Wheel 包下载圆满完成。结合前文 x86 的排查记录，两种架构的离线包准备工作均已就绪。
